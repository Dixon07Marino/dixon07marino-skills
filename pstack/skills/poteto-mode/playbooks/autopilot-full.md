### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until a verifier that never wrote the code has proven the code that lands.**

A verdict covers one patch and green CI covers one head. The patch-id rule in `playbooks/shipping.md` can carry a verdict across a rebase, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR.** Resolve the forge from `git remote get-url origin`: `github.com` uses `gh`, and `dev.azure.com` or `visualstudio.com` uses `az repos pr` (Azure DevOps CLI). Never require Graphite (`gt`). Each owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 3 and 4 clear it. Where babysit says to report a rebase, the owner rebases its own branch and publishes it with `git push --force-with-lease`. The code is ready after the slop-strip and the `/no-comments` pass. Rebase onto current trunk and report the code-ready head before self-proof. Push each finished unit before starting the next, and force-push only your own branch, pinned to the SHA you last pushed.
3. **Verify once with one independent verifier.** It runs at the code-ready head, re-runs the gates, proves the load-bearing behavior live on the real surface, and audits the diff. A rebase or minor fix gets a quick re-check at the new head, and a wording-only change gets none. Block a PR only for a problem you can show: a failing run at the head, or a doc line the PR made wrong. A problem the base already has does not block unless the PR copies it or newly reaches it. Everything else goes in a follow-up.
4. **The owner merges only what was verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Right before merging, fetch trunk and ask whether its changes can affect the patch. Rebase and wait for CI when the code that would land was never tested, as with a conflict or a file both sides changed. When trunk changed a caller of the patch or something it depends on, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase, hold and report.
5. **Never loosen a gate on the owner's word.** A raised budget or an allowlist entry needs the verifier's proof and your fresh countersign. A disabled or soft-failed check always comes out. Never give or bypass an approval the forge enforces.
6. **Stand down at once on the operator's stop.** Each owner reports where it stands and keeps its brief until the operator releases it.

**Reply:** each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR.
